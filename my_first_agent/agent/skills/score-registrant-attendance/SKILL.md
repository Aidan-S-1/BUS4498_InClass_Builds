# score-registrant-attendance

## User inputs
On each run, the user supplies:
- The current registration list: one row per registrant with registrant ID, days before the event they registered (or the registration timestamp plus the event date), solo or team signup, team name if any, any cancellation or change made through the form, and the contact count (how many confirmation messages that person has already received for this event).
- Prior attendance records matched to registrant IDs: past CPVC events registered for and whether the person checked in.
- Confirmation responses: each registrant's status (yes, maybe, no, or no reply) plus the reply text and time.
- The event name, event date, and which checkpoint this is (14-day, 7-day, 2-day) and whether this is a first pass or a rescoring pass after T6.
- Optional: an updated set of scoring weights approved through H2 and stored by T13. If none is supplied, use the defaults in references/scoring-rules.md and say so in the output.

If the registration list, the event date, or the confirmation statuses are missing, ask for them before scoring anything. If a registrant's contact count is blank, do not assume zero: treat that person as already at the two-message limit and flag the count for an organizer to confirm. If the inputs are dated from an earlier checkpoint than the one requested, ask whether they are current before continuing.

## Procedure
1. Read the inputs and confirm that the registration list, event date and checkpoint, confirmation statuses, and attendance records are present and current; ask for anything essential that is missing before scoring.
2. For each registrant, collect the signals: days before the event they registered, past attendance (checked in, registered but no check-in, or no history), confirmation status, team signup, any cancellation, and contact count; mark every signal that is not in the inputs as unknown rather than guessing.
3. Apply the current scoring weights to each registrant's structured signals to produce a baseline score from 0 to 100 and a provisional label, recording which signals were present and which were unknown.
   - Use [scoring-rules.md](references/scoring-rules.md): Before deciding anything in this step, read the matching section of this reference and apply it as written: section 1 weights and overrides plus section 2 label cutoffs (step 3); section 3 unclear replies and the handoff rule for non-attendance replies (step 4); section 4 missing history (step 5); section 5 conflicts and possible duplicates (step 6); section 6 candidate eligibility, including never assuming a blank contact count is zero (step 7); section 7 retry limits (every step). Never edit these rules; if the user supplies a H2-approved weights update, use it instead and say so in the score sheet.
   - Use [score_registrants.py](scripts/score_registrants.py): In step 3, save the registrant rows as a CSV with the columns listed in the script's docstring (registrant_id, days_before_event, signup_type, team_name, cancelled, contact_count, past_attended, past_no_show, confirmation, reply_text) and run: python scripts/score_registrants.py registrants.csv — add --weights weights.json only when a H2-approved weights file was supplied. Requires Python 3, standard library only. Read the JSON output: score, label, signals_used, signals_unknown, flags, and confirmation_candidates. Treat it as the baseline only: it cannot read reply text, so after step 4 changes a reply's signal, rerun it with the adjusted confirmation value. Expected check: the sample row in the docstring scores 100 / likely. If Python is unavailable, apply the weights table from the reference by hand and state that the script was not run.
4. Interpret any free-text reply that does not map cleanly to yes, maybe, or no into an adjusted confirmation signal, quoting the registrant's wording; after one extra attempt, record the signal as unknown.
   - Use [scoring-rules.md](references/scoring-rules.md): Before deciding anything in this step, read the matching section of this reference and apply it as written: section 1 weights and overrides plus section 2 label cutoffs (step 3); section 3 unclear replies and the handoff rule for non-attendance replies (step 4); section 4 missing history (step 5); section 5 conflicts and possible duplicates (step 6); section 6 candidate eligibility, including never assuming a blank contact count is zero (step 7); section 7 retry limits (every step). Never edit these rules; if the user supplies a H2-approved weights update, use it instead and say so in the score sheet.
5. For registrants with no matched attendance history, look only inside the supplied inputs for fallback evidence such as a team whose other members attended before, and never treat missing history as evidence of not attending.
   - Use [scoring-rules.md](references/scoring-rules.md): Before deciding anything in this step, read the matching section of this reference and apply it as written: section 1 weights and overrides plus section 2 label cutoffs (step 3); section 3 unclear replies and the handoff rule for non-attendance replies (step 4); section 4 missing history (step 5); section 5 conflicts and possible duplicates (step 6); section 6 candidate eligibility, including never assuming a blank contact count is zero (step 7); section 7 retry limits (every step). Never edit these rules; if the user supplies a H2-approved weights update, use it instead and say so in the score sheet.
6. Resolve signals that disagree by preferring the most recent and most direct evidence, or flag the conflict; treat two records that may belong to the same person as an identity question for the organizers rather than deciding it.
   - Use [scoring-rules.md](references/scoring-rules.md): Before deciding anything in this step, read the matching section of this reference and apply it as written: section 1 weights and overrides plus section 2 label cutoffs (step 3); section 3 unclear replies and the handoff rule for non-attendance replies (step 4); section 4 missing history (step 5); section 5 conflicts and possible duplicates (step 6); section 6 candidate eligibility, including never assuming a blank contact count is zero (step 7); section 7 retry limits (every step). Never edit these rules; if the user supplies a H2-approved weights update, use it instead and say so in the score sheet.
7. Identify confirmation candidates: registrants labeled uncertain with no usable reply whose contact count is below two, ranked by how close their score is to the midpoint, and leave out anyone at the limit or with a missing count.
   - Use [scoring-rules.md](references/scoring-rules.md): Before deciding anything in this step, read the matching section of this reference and apply it as written: section 1 weights and overrides plus section 2 label cutoffs (step 3); section 3 unclear replies and the handoff rule for non-attendance replies (step 4); section 4 missing history (step 5); section 5 conflicts and possible duplicates (step 6); section 6 candidate eligibility, including never assuming a blank contact count is zero (step 7); section 7 retry limits (every step). Never edit these rules; if the user supplies a H2-approved weights update, use it instead and say so in the score sheet.
8. Finalize each registrant's likelihood and label with the signals that support it, mark anyone escalated before a supported score as undetermined, and note every unresolved case with the exact open question.
9. Fill the score sheet template with the run details, the score table, the confirmation candidates, the evidence summary, the unresolved issues, and the handoff note, and return it.
   - Use [score-sheet-template.md](assets/score-sheet-template.md): When producing the final result in step 9, copy this template's headings exactly and replace every bracket with this run's facts. Keep every section even when the answer is "none" or "Not applicable". Quote reinterpreted reply wording only in the Evidence summary, never in a form that names a registrant outside the organizing team. The last section must name T4 for completed scores and the organizer review queue for unresolved cases.

## Output
Return one completed score sheet (Markdown) with these sections: run header (event, date, checkpoint, first pass or rescoring, weights used, registrants scored out of total); status (completed or escalated); a score table with one row per registrant showing registrant ID, likelihood 0–100, label (likely / uncertain / unlikely / undetermined), the signals behind the score, the signals that were unknown, and flags; the confirmation-candidate list with each candidate's contact count (or the word none); an evidence summary that quotes any reinterpreted reply wording; subtasks performed, including repeated attempts; unresolved issues (or none); a handoff note (or Not applicable); and the next recipient, which is T4 for completed scores and the CPVC organizer review queue for unresolved cases.

The result should make three things visible at a glance: which signal drove each score, which registrants still cannot be scored and why, and who may still be contacted without breaking the two-message limit. Every number must trace to a stated signal; never show an unexplained score.

## Boundaries
Do not aggregate scores into a forecast range or recommend food, drink, or swag quantities; that is T4 and T8.
Do not send, draft, or schedule any message to a registrant; only list confirmation candidates. Sending belongs to T5.
Do not change the scoring weights, label thresholds, or tolerance band; that is T12 and H2. Apply them exactly as supplied or as stored in references/scoring-rules.md.
Do not merge, edit, or delete registration records, and do not decide whether two records are the same person; flag it for the organizers.
Do not search outside the supplied inputs (no social media, no other club rosters, no guesses about personal circumstances).
Do not disclose an individual registrant's reply outside the organizing team; quote reply wording only inside the score sheet's evidence column.
Ask me before scoring when the registration list, event date, or confirmation statuses are missing or appear stale.
Stop and hand off to the CPVC organizer review queue when: a possible duplicate registration cannot be matched with confidence; a reply raises something other than attendance (a question, complaint, or accessibility request); the retry limits in the reference are reached; the 20-inference-request budget is exhausted; or finishing a score would require contacting a registrant. When handing off, still return the score sheet with the completed rows, label the affected registrants undetermined, and write the exact open question in the handoff note.
